# Site

The landing page and the static half of the add-a-friend-by-link flow. Nothing
here is built or bundled with the app — it is deployed on its own and
referenced by URL.

**Live at `https://routro.vercel.app`** (Vercel project with Root Directory
set to `site`, framework preset "Other", no build command).

| File | Purpose |
| --- | --- |
| `index.html` | The landing page. |
| `styles.css` | All of its styling. Mirrors `src/theme/tokens.ts` — the phone mockups are hand-built CSS, so the token block at the top is what keeps them looking like the app. |
| `main.js` | Resolves the download links, including which architecture's APK to offer. |
| `release.json` | Generated by `scripts/release-apks.ts`. What both pages read instead of the GitHub API. Do not edit by hand. |
| `i/index.html` | The page an invite link opens. Reads `?u=<public_uid>` and offers "Open in Routro". Self-contained — it shares no CSS or JS with the landing page. |
| `robots.txt` / `sitemap.xml` | Index the landing page, not the personal invite URLs. |
| `.well-known/assetlinks.json` | Proves to Android that this domain and the app belong together, so verified links skip the page and open the app directly. |

There is still no build step. The CSS and JS are separate files rather than one
inlined blob because the page outgrew being edited as a single document, not
because anything bundles them.

## The download section

Releases carry four APKs — one per architecture plus a universal build — named
by `scripts/release-apks.ts` as `routro-v<version>-<abi>.apk`. `main.js` matches
release assets on that `-<abi>.apk` suffix, so **renaming the assets breaks the
download page**, quietly: it falls back to the releases URL and nobody hears
about it.

**The pages do not call the GitHub API.** `scripts/release-apks.ts` also writes
`release.json` — about a kilobyte listing each build's ABI, size, SHA-256 and
download URL — and that is what `main.js` and `i/index.html` read, from this
origin.

The API worked, but its unauthenticated limit is 60 requests an hour **per IP**,
and behind carrier-grade NAT one address stands for a great many people. For an
app aimed at Delhi commuters on mobile data, that is a download button that
degrades exactly when it is busiest. Same-origin JSON has no ceiling, no CORS
preflight, and no dependency on GitHub's API being reachable.

The APKs themselves stay on GitHub Releases and cannot move here: GitHub blocks
any file over 100 MiB and the universal build is ~145 MiB; a Vercel Hobby
deployment caps at 100 MB of static files against ~320 MB of APKs; and git keeps
every old blob forever, so "replacing" them each release would grow the repo
permanently rather than swapping anything out.

**The cost is one step in the release flow: `release.json` has to be committed
and pushed for a new version to appear on the site.** Nothing breaks if that is
forgotten — the page keeps offering the previous release — but it will quietly
stay a version behind, so `release-apks.ts` prints a reminder.

Which build a visitor is offered is a guess, and the page is built to admit
that. The detection order is:

1. Architecture tokens in the user-agent string (`aarch64`, `armv7`, …), which
   some browsers — Firefox for Android among them — still carry.
2. `navigator.userAgentData.getHighEntropyValues(['architecture', 'bitness'])`.
3. Bitness alone, which is the ordinary case: **measured on Android Chrome 148,
   `architecture` comes back as the empty string and only `bitness` is
   populated.** 64-bit is taken to mean arm64, which is true of essentially
   every phone; 32-bit means armeabi-v7a, and rescuing that case is most of why
   the hint is read at all.
4. arm64, as the default that is right far more often than not.

Anything past step 2 is labelled a guess on the page and opens the full list of
builds, because the visitor is then the only one who knows the answer.

`i/index.html` does a cut-down version of the same thing: UA tokens, then
bitness, then arm64 — falling back to universal rather than to the next
architecture along, because universal is the one build guaranteed to run
anywhere. It deliberately has no chooser: it is a page for someone who was
handed a link, not a download page. The bitness check is there for one reason —
handing a 32-bit phone an arm64 build produces an APK that will not install, and
the person seeing that was invited by a friend.

## The domain-root constraint

Android only ever looks for asset links at **`https://<host>/.well-known/assetlinks.json`** —
the root of the domain, never a subpath. `https://example.com/project/.well-known/…`
is not consulted and App Links will silently stay unverified.

That is why this is its own Vercel project rooted at `site/` rather than a page
inside the app repo's site. Any host giving you the domain root works the same
way — Netlify, Cloudflare Pages, S3, or a custom domain.

**Use the production domain, never a preview URL.** Every Vercel preview
deployment gets its own hostname, and App Links only verify the exact host
compiled into the manifest.

**No `vercel.json` is needed.** Vercel serves `.well-known/assetlinks.json` with
the right content type on its own, `/i/` resolves to `index.html` by default,
and the default cache policy for static files already revalidates — pinning a
`max-age` here would only make a fingerprint update take *longer* to propagate.
(The Vercel bug you may find in searches is about `apple-app-site-association`,
which is extensionless and gets mis-typed. If iOS Universal Links are ever added,
that one file will need an explicit `Content-Type` header in `vercel.json`.)

## Why the invite page is at `/i/`, not `/`

The App Links `pathPrefix` in `app.json` is scoped to `/i`, which is what left
the root free for the landing page — and is also what you want behaviourally. A
`/` prefix would mean tapping *any* link to this domain tries to open the app,
including someone sharing the landing page itself.

Keep it that way. Adding pages at the root costs nothing; widening the prefix
would break sharing the site.

## Pointing the app at it

Wherever you publish, two values have to agree:

| Where | What |
| --- | --- |
| `INVITE_BASE_URL` in `src/friends/inviteLink.ts` | Full URL of the page, trailing slash included |
| `expo.android.intentFilters[].data.host` (+ `pathPrefix`) in `app.json` | Same host, same path prefix |

The second is native config, so it needs a rebuild to take effect. The first
takes effect on the next JS bundle.

## The fingerprint

`assetlinks.json` carries the SHA-256 of the key EAS signs release builds with.
If it ever needs re-reading:

```bash
npx eas credentials -p android
```

Pick the `production` profile and copy the value shown as **SHA256 Fingerprint**
(uppercase hex, colon-separated, 32 pairs). `keytool -printcert -jarfile <apk>`
reports the same thing from an already-built APK.

### When the fingerprint changes

Not per release. It identifies the **signing key**, not the build, so it stays
put across every new version as long as the key does. It only changes when:

- **You ship through Google Play.** Play App Signing re-signs your upload with
  Google's own key, so the fingerprint Android checks becomes Google's, not
  EAS's. Take it from Play Console → Release → Setup → App signing.
- **The keystore is rotated or regenerated** on EAS.
- **Different profiles use different keys.** `sha256_cert_fingerprints` is an
  array — list every key you ship under. Direct-download APKs signed by EAS plus
  Play-signed installs means both go in.

Getting it wrong is quiet: verification just fails and links fall back to the
web page, with nothing in the app to tell you why. `adb shell pm get-app-links`
below is how you find out.

## Verifying it works

After a build that includes the intent filters is installed:

```bash
adb shell pm get-app-links com.routro.app
```

The host should be listed as `verified`. If it says `legacy_failure` or
`unverified`, Android either couldn't fetch the file, or the fingerprint didn't
match the one the installed APK was signed with. Re-check with:

```bash
adb shell pm verify-app-links --re-verify com.routro.app
```

Note that verification needs network access on first install and can lag by a
few seconds.
